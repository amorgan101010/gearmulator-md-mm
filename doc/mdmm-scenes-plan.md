# MD/MM scenes and crossfader: implementation plan for Luna

Status: MD and MM MIDI-scene v1 are implemented. Scene banks are keyed by the active Kit slot (64 MD Kits, 128 MM Kits); patterns that use the same Kit share its scenes. It drives interpolated parameter CCs from the controller timer and keeps a per-Kit clean base snapshot for restoration. Side mute falls back to the clean Kit value without clearing the scene assignment. The local and standalone remote panels expose assignment, mute, fader, edit mode, lock editing, clear-lock, and clear-scene controls. This is an approximation, not firmware-level OT scene priority.

### Spike result so far

Normal UI/host parameter writes enter firmware as MIDI CCs, while the sequencer and trig locks execute inside firmware. There is no observed post-lock parameter hook, so v1 sends the interpolated CC values periodically and cannot guarantee OT-style priority over trig locks. It snapshots base values from each accepted coherent Kit dump, tracks explicit UI/DAW edits separately, sends those base CCs when a lock stops controlling an address, and never routes scene output through host automation publication. Device feedback matching a scene CC is ignored to keep it out of the clean base. Device feedback with another value is ambiguous (front-panel edits and trig-lock output share this path), so v1 does not use it to mutate the base snapshot. This protects the saved Kit baseline, but means unsaved front-panel edits are not guaranteed to become the return value. The approach intentionally chooses restoration safety over exact live-base tracking.

### Prototype contents

- Added `md::scene::Bank` / `Store` with sparse address locks, clean base values, A/B assignments, side mute, fader position, interpolation, and a bounded, validated scene snapshot. The plugin saves it as optional chunk `SCEN`; the inner scene payload is version 3 and migrates versions 1 and 2. MM scenes use the active Kit ID, not the Pattern ID.
- Added a 54dp scene strip below both faceplates. Click A/B to enter or leave edit mode, then click a trig to assign that scene. While editing, data encoders change a scene lock on the selected track/page; clear-lock removes the last edited address and clear-scene removes every lock in the assigned scene while preserving its A/B assignment. MM supports its seven parameter pages and six tracks. Encoder turns in scene mode are consumed instead of changing the firmware Kit.
- Fader changes send CC updates on the controller's 16ms tick, with unchanged active values refreshed every 50ms. The fader is not an automatable plugin parameter. Conflicting trig locks can override a scene between refreshes, and matching feedback suppression cannot identify every firmware-side lock. Built-in MD/MM, installed Pinkmonodrum MD/MM, and installed StealthClassic MD/MM skins include the strip.
- The remote panel's `C <json>` stream reports the current Kit bank state. Its `sc` commands control assignments, fader, mute, edit side, trig assignment, scene encoder edits, and clearing the current edited-side lock.

## Behavior to reproduce

The [Octatrack MKII manual, sections 10.3–10.3.5](https://www.elektron.se/wp-content/uploads/2024/09/Octatrack-MKII-User-Manual_ENG_OS1.40A_210414.pdf) defines 16 scenes per *part*. A scene holds sparse parameter locks. Assign any scene to A and any scene to B, including the same or an empty scene. The left and right fader ends fully select A and B. At intermediate positions, interpolate each address between its A and B values; an unlocked side uses the current general parameter value. Two empty scenes are neutral. Octatrack scene locks override trig locks while the fader moves. It also has scene mute, copy/paste/clear, and special equal-energy volume locks; those are later milestones here.

MD/MM have no Octatrack parts. Use the **active Kit slot** as the scene bank in the first version: 16 sparse scenes and A/B assignments per Kit. Pattern changes that keep the Kit keep the scenes; a different Kit selects its own bank. This is a plugin extension, not a claim that the original MD firmware understands scenes. Persist banks in the plugin project state. Confirm how Kit changes, unsaved Kit edits, and Kit reloads behave before implementing this identity rule.

## User interaction

1. Add an A button, horizontal crossfader, and B button in a compact **Scenes** strip adjacent to the existing panel, without moving or intercepting the 16 firmware trig keys. Show `A 01` and `B 02` (or their assignments), fader position, and whether each assigned scene has locks. Give the strip the MD skin's existing button/material styling. A skin missing the optional strip must still open.
2. Clicking A or B selects which side is being edited. While that side is held or latched, clicking an existing trig key 1–16 assigns its corresponding scene **in the plugin**; suppress that click's firmware trig action. Normal trig clicks retain their current behavior. The selected side and scene number must remain visible after release. Make mouse, keyboard, and gamepad behavior explicit; do not silently steal existing shortcuts.
3. While editing a side, turn the existing data-entry encoders on the selected track/page to set scene locks. Show the locked value and a clear lock marker without replacing the firmware's base-value display. Press the corresponding encoder to clear that scene lock; use an explicit clear control if encoder press conflicts with an MD function. Changing tracks/pages lets one scene span all tracks. Editing a scene must not change the base Kit or host automation parameter.
4. Provide a simple `Clear scene` action with confirmation, plus `Copy scene`/`Paste scene` if the current editor menu makes these cheap. Scene mute and Octatrack's extra XLV/XVOL/XDIR volume semantics can follow after the core morph is reliable. Ordinary MD volume/level interpolation is acceptable initially, but label it as ordinary level interpolation.
5. The fader is an absolute 0–127 control, controllable by drag and keyboard. V1 saves the fader position but does not expose a host automation parameter; a stable appended parameter ID can follow once the MIDI behavior is proven. A/B assignment change at a fixed fader position updates the sound on the next controller tick.

## Data and runtime model

Represent a lock by `(track, page, index) -> 0..127`, plus a presence bit; zero is a valid locked value. Keep 16 scenes, the two assigned scene numbers, and fader position in a Kit bank. Keep **base/general values** separate from (a) scene lock values, (b) calculated fader output, and (c) firmware's current live value after sequencer locks. For one address, use `A = hasLockA ? valueA : base`, `B = hasLockB ? valueB : base`, `output = round(A + (B-A)*position/127)` with exact endpoint values. Compute only for addresses locked in either assigned scene; leave all other addresses untouched. Clamp and step categorical parameters instead of interpolating through undefined states. Mute and machine assignment are excluded from the first pass; define an explicit allowlist of supported MD parameter addresses after the runtime spike.

The current `md::automation::ParameterChange` address and MD/MM CC encoder in `mdLib/mdautomation.h/.cpp` are useful for identifying supported parameters. `mdController.cpp` owns the synchronized Kit snapshot and per-address automation publications; `getTrackParameterValue()` already feeds current encoder value queries. **Do not feed scene output through `Parameter::setUnnormalizedValue*()` or `publishAutomationIntent()`**: that would overwrite the base/host automation value, enter the `AUTO` snapshot, and possibly feed back into the UI. Treat scene output as a separate runtime layer. On an actual base edit or DAW automation write, update the base first and recompute the affected output. On scene edit, update only the lock layer. On Kit change or state restore, suspend scene output until the relevant base Kit snapshot is coherent, then apply the selected bank once.

### Required feasibility spike before the runtime implementation

Trace one MD address (for example track 1 filter base) through: firmware encoder edit, host automation, incoming CC, Kit dump, trig parameter lock, and outgoing MIDI during pattern playback. Test whether sending a CC to create a temporary fader value mutates the firmware's Kit/live base value, whether the sequencer overwrites it at each trig, and whether a Kit dump reports the original or morphed value. Record the findings in this document. The existing controller's stored-Kit dump is explicitly distinct from unsaved live edits, so it cannot be assumed to be the complete base source.

The long-term target remains a non-destructive override after firmware trig locks. V1 uses periodic CC updates as an explicitly approximate MIDI implementation: it preserves the coherent Kit dump baseline and applies explicit UI/DAW edits to that baseline, but it cannot see front-panel edits separately from sequencer-lock output and cannot guarantee lock priority. Replace the CC overlay with a bounded MD-only firmware/emulator hook if future investigation identifies a safe parameter-application point.

The controller currently processes host automation through a bounded realtime queue (`mdController.cpp`, `mdRealtimeQueue.h`). A fader movement must publish one latest position, not enqueue a burst for every parameter and every drag event. Recompute only affected addresses at a bounded rate or at actual parameter-write boundaries; skip unchanged quantized outputs. State transfer between UI/control and audio threads must avoid mutexes, allocations, and unbounded scans in the audio callback. Keep scene work within the existing MD performance budget, especially at 512-frame standalone playback.

## Persistence and lifecycle

Add the optional `SCEN` chunk beside `AUTO` in `mdPluginProcessor.cpp` (`saveChunkData` / `loadChunkData`). The chunk is MD-only and stores Kit bank ID, clean base values, A/B assignment, fader position, and sparse address/value locks, with strict bounds and duplicate-address validation. Missing `SCEN` means empty scenes and a neutral fader; unknown future payload versions fail safely without harming firmware or `AUTO` state. Save scene data with the editor closed. Restore scene data with project state and apply only after the active Kit snapshot is coherent. Never save temporary fader output as a Kit or automation value. Check project save/load, standalone state, and editor close/reopen separately.

## Suggested implementation order

1. **Runtime spike and baseline:** capture the six parameter paths above; decide and document the non-destructive injection point and parameter allowlist. Build a small MD test demonstrating base value restoration and trig-lock precedence before drawing the UI.
2. **Pure scene model:** sparse locks, assignment, interpolation, empty-scene fallback, quantization, Kit-bank switching, and serialization. Test endpoints, both-sides-locked, one-side-locked, same-scene assignment, lock value zero, clear, and malformed state.
3. **MD runtime:** apply the scene layer through the proven injection point, connect Kit changes and real base edits, and add one host-automatable fader. Test playing patterns with parameter locks while sweeping; verify that disabling/clearing scenes returns to the live general value and that saving/reloading a Kit does not capture the morph.
4. **MD UI:** add the strip to `skins/mdDefault/mdDefault.rml`/RCSS and wire `mdEditor.cpp` using existing `ElemButton`, trig keys, encoder event handling, and Rml range input. Keep `machineRack` geometry in mind (it currently occupies the 196dp strip below the 570dp faceplate); choose an added or collapsible area instead of overlaying its controls. Verify optional/missing skin elements and editor reopen.
5. **Persistence and regression:** project/standalone round trips, Kit and pattern switches, MIDI input, CPU at 512 frames, and MD/MM playback with all scenes empty. MM now uses the shared model and strip with its six tracks and seven parameter pages. Add scene mute and any special volume fade mode only as separate increments.

## Acceptance demonstration

On a running MD pattern, set a filter lock in scene 1 and a different lock for the same address in scene 2; assign them A/B and hear continuous changes across the fader with exact values at both ends. Put a lock on only one side and confirm the other end follows a live base edit. Put locks on two tracks/pages and confirm both move. Play a trig with a conflicting parameter lock and confirm the scene has priority while active, then clear/mute the scene and hear the trig/base behavior return. Save, close, reopen, switch Kits, and reload the original Kit: scene data must survive while the unmodified Kit value remains intact. With all scenes empty, audio and UI behavior should match the current build.
